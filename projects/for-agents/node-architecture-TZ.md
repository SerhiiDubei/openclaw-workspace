# ТЗ: Node-Based Architecture Visualization for Island Simulation

## 1. Контекст

**Проєкт:** Island Simulation (TimeWars — окремо, поза цим ТЗ)  
**Проблема:** Система складається з багатьох модулів/підсистем/мікросервісів, які взаємодіють. Поточні візуалізації не дають повної картини: незрозуміло, що існує, що заплановано, що недороблено, які зв'язки між компонентами. Кожне доповнення системи ускладнює розуміння загальної архітектури.

**Ціль:** Створити інтерактивну node-based візуалізацію архітектури, яка показує 4 фази розвитку системи та дозволяє досліджувати кожен компонент і зв'язок детально.

---

## 2. Загальні вимоги

### 2.1 Формат
- **Node-based граф** (ноди з'єднані стрілками/лініями)
- Інтерактивність: клік на ноду/зв'язок відкриває детальну інформацію
- Масштабованість: можливість zoom in/out, drag для навігації
- Можливість згортати/розгортати складні ноди (з під-нодами)

### 2.2 Чотири фази/шари (мають візуально відрізнятися)

| Фаза | Колір/стиль | Опис |
|------|-------------|------|
| **Legacy** | Сірий, muted | Попередні візуалізації, історичні архітектури, куди рухалися раніше |
| **Planned** | Синій/фіолетовий | Те, що було заплановано, але ще не реалізовано |
| **Current** | Зелений/жовтий | Те, що зараз існує (з позначкою "білих дірок" — недороблених частин) |
| **Future** | Помаранчевий/червоний | Те, що планується додати/розширити |

**Примітка:** Один і той самий функціонал може існувати в кількох фазах (наприклад, запланований модуль став Current, але в ньому ще є білі дірки).

## 3. Структура ноди

### 3.1 Типи нод

**Проста нода:**
- Одна конкретна функція/сервіс
- Приклад: "Logger", "Auth Service", "Weather API"

**Складна нода (контейнер):**
- Має внутрішню структуру з під-нод
- Приклад: "World Engine" → всередині Terrain Generator, NPC System, Weather System
- Візуально відрізняється (подвійна рамка, або інший shape)

### 3.2 Вміст ноди (що видно без кліку)
- **Назва** — коротка, зрозуміла
- **Тип** — іконка або badge (Service, Module, Engine, API, etc.)
- **Статус** — колір рамки або background вказує на фазу
- **Health indicator** (опціонально) — чи працює зараз

### 3.3 Детальний вигляд ноди (при кліку)

```
┌─────────────────────────────────────┐
│  [Назва ноди]                       │
│  Тип: [Service/Module/Engine]       │
│  Фаза: [Current/Planned/etc]        │
├─────────────────────────────────────┤
│  ЩО ЦЕ РОБИТЬ:                      │
│  [Опис простою мовою: що ця нода    │
│   виконує, яку проблему вирішує]    │
│                                     │
│  ЩО ВСЕРЕДИНІ:                      │
│  - [Компонент 1]                    │
│  - [Компонент 2]                    │
│  - [Білі дірки — що недороблено]    │
│                                     │
│  ЩО ПЕРЕДАЄ ДАЛІ:                   │
│  [Дані/події, що виходять з ноди]   │
│                                     │
│  ЕФЕКТ/ВПЛИВ:                       │
│  [Який результат дає ця нода        │
│   для загальної системи]            │
└─────────────────────────────────────┘
```

## 4. Структура зв'язків (edges)

### 4.1 Типи зв'язків (візуально різні кольори/стилі ліній)

| Тип | Стиль | Опис |
|-----|-------|------|
| **Active** | Суцільна зелена лінія | Працюючий зв'язок, дані передаються |
| **Planned** | Пунктирна синя | Запланований зв'язок, ще не реалізований |
| **Broken/Missing** | Червона пунктирна або з хрестиком | Зв'язок має бути, але не працює/немає |
| **Deprecated** | Сіра dashed | Зв'язок був, зараз не використовується |
| **Bi-directional** | Подвійна стрілка | Двосторонній обмін даними |

### 4.2 Вміст зв'язку (при кліку на лінію/стрілку)

```
┌─────────────────────────────────────┐
│  [Нода A] → [Нода B]                │
│  Тип: [Active/Planned/Broken]       │
├─────────────────────────────────────┤
│  ЩО ПЕРЕДАЄТЬСЯ:                    │
│  [Формат даних, події, API calls]   │
│                                     │
│  ЧАСТОТА/ТРИГЕР:                    │
│  [Real-time / On-event / Scheduled] │
│                                     │
│  СТАТУС ПРОБЛЕМ:                    │
│  [Якщо broken — чому, що потрібно   │
│   для фіксу]                        │
└─────────────────────────────────────┘
```

## 5. Приклади нод для Island Simulation

*Це приклади — потрібно узгодити реальний список з контекстом системи*

**Core ноди:**
- `World Engine` (складна) — генерація та управління світом
- `Time System` — управління часом, циклами
- `Player Manager` — стан гравця, інвентар, прогрес
- `Event Bus` — центральна шина подій

**Integration ноди:**
- `AI Module` — LLM інтеграція, NPC діалоги
- `Persistence Layer` — збереження стану
- `API Gateway` — зовнішні API

**Feature ноди:**
- `Quest System` — квести, завдання
- `Economy Engine` — ресурси, торгівля
- `Social System` — взаємодія між гравцями

## 6. Технічні вимоги

### 6.1 Рекомендовані бібліотеки/інструменти
- **React Flow** — найпопулярніше рішення для node-based UI
- **D3.js + dagre** — для складних layout алгоритмів
- **Cytoscape.js** — для великих графів
- **Excalidraw API** — якщо потрібен hand-drawn стиль

### 6.2 Формат даних (приклад)

```json
{
  "nodes": [
    {
      "id": "world-engine",
      "type": "container",
      "name": "World Engine",
      "phase": "current",
      "description": "Генерує та управляє ігровим світом",
      "internals": ["Terrain Gen", "Weather", "NPC Spawner"],
      "gaps": ["Procedural cities not implemented"],
      "outputs": ["world-state", "events"],
      "impact": "Визначає все, що бачить гравець",
      "position": { "x": 100, "y": 200 }
    }
  ],
  "edges": [
    {
      "id": "e1",
      "source": "world-engine",
      "target": "player-manager",
      "type": "active",
      "dataType": "WorldState",
      "frequency": "real-time"
    }
  ]
}
```

## 7. Етапи реалізації

**Мінімальний viable продукт:**
1. Базова сітка з нодами (4-5 основних)
2. Кольорове кодування фаз
3. Клік на ноду — модалка з описом
4. Базові зв'язки (стрілки)

**Ітерація 2:**
- Складні ноди з під-нодами
- Клік на зв'язки
- Фільтри по фазах

**Ітерація 3:**
- Drag-and-drop
- Редагування inline
- Export

## 8. Питання для уточнення

Перед стартом потрібно узгодити:

1. **Список всіх нод** — які модулі/системи зараз існують?
2. **Що є Legacy?** — які архітектури були раніше?
3. **Що є "білими дірками"?** — конкретний список недоробленого
4. **Які зв'язки вже працюють, які тільки плануються?**
5. **Пріоритет:** web-додаток, чи інтеграція в існуючий інструмент?
